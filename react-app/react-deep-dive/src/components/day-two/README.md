# День 2. `useState` и концепция Immutability

## Три факта, из которых следует всё остальное

1. **Компонент это функция, а рендер это её вызов.** Каждый вызов получает свой «снимок» (snapshot): состояние, пропсы и
   все обработчики внутри этого вызова привязаны к значениям этого рендера. Это обычные константы замыкания.
2. **`setState` ничего не считает.** Он кладёт запись в очередь обновлений хука и просит React сделать рендер.
3. **Очередь обрабатывается при рендере.** React берёт базовое состояние и последовательно прогоняет записи.

## useState

https://habr.com/ru/companies/otus/articles/667706/

`useState` хук, который позволяет сохранять состояние внутри компонента. Возвращает массив из двух значений:
текущее состояние (1) и функция для его изменения (2).

```ts
const [count, setCount] = useState(0);
```

Состояние хранит React (внутри своей структуры для компонента), а не переменная функции.
Функция компонента вызывается при каждом рендере заново, и состояние (1) каждый раз получает значение из хранилища React.
Поэтому состояние (1) внутри одного рендера константа: это снимок (snapshot).

Функция для его изменения (2) не меняет переменную, а просит React отрисовать компонент заново с новым значением.

Ленивая инициализация: если начальное значение дорого вычислять, передайте функцию. Она вызовется один раз при первом рендере:

```ts
const [project, setProject] = useState<Project>(() => ({ name: null, owner: null, tasks: [] }));
```

### Почему `console.log(count)` после `setCount(count + 1)` показывает старое значение

`count` в этом замыкании константа, и она не изменится никогда, даже после рендера. Новое значение увидит
**следующий** вызов компонента с новым обработчиком, а старый обработчик продолжит видеть старое.

## Очередь обновлений: значение и функция

В очередь можно положить два вида записей:

- **значение**: `setCount(5)`, `setCount(count + 1)`. Оно уже посчитано в момент вызова и «запечено» в запись;
- **функция (апдейтер)**: `setCount(prev => prev + 1)`. Она вызовется позже, при рендере, и получит накопленное состояние.

Значение заменяет результат, функция получает то, что накопилось к этому моменту:

```ts
setCount(count + 1); setCount(count + 1); setCount(count + 1);
// очередь [1, 1, 1] → 0 → 1 → 1 → 1, итог 1 (+1)

setCount(prev => prev + 1); setCount(prev => prev + 1); setCount(prev => prev + 1);
// очередь [f, f, f] → 0 → 1 → 2 → 3, итог 3 (+3)

setCount(5); setCount(p => p + 1); setCount(p => p * 2);  // 5 → 6 → 12
setCount(p => p + 1); setCount(p => p * 2); setCount(5);  // последнее значение перезаписывает всё, итог 5
```

`setCount(count + 1)` для React равно `setCount(() => count + 1)` с уже подставленным значением.

Аналогия из SQL: `UPDATE ... SET count = count + 1` (формула применяется к текущему значению) против «прочитали в приложении,
посчитали, записали» (потерянное обновление).

## Правило апдейтера: считайте из `prev`

> Всё, что зависит от прежнего состояния, считайте **внутри** апдейтера, из `prev`.

Параметр `prev` сам по себе ничего не гарантирует. Важно, **что функция читает внутри**. Типичная ошибка, при которой
апдейтер есть, а защиты нет:

```ts
function handleDoneTask(id: number) {
  setProject((prev) => {
    const newTasks = project.tasks.map(...);   // project это снимок, а не prev
    return { ...prev, tasks: newTasks };
  });
}
```

Если вызвать два таких обработчика подряд в одном блоке, оба посчитают `tasks` от одного снимка, и второй затрёт первый:
`prev` участвует только в `...prev` (для остальных полей), а `tasks` внутри записи это константа из замыкания.

Правильно: апдейтер самостоятельная формула `следующее = f(prev, аргументы)`:

```ts
setProject((prev) => ({
  ...prev,
  tasks: prev.tasks.map((t) => (t.id === id ? { ...t, done: !t.done } : t)),
}));
```

Проверка в голове: если вынести апдейтер за пределы компонента, и ему понадобилась переменная из состояния
(`project`, `count`, `items`), он зависит от снимка и написан неверно. Допустимы только аргументы (`id`, `value`, `title`).

То же касается объекта целиком: `setProject({ ...project, name })` копирует **весь** снимок и перезаписывает им актуальные поля.
Правильно `setProject(prev => ({ ...prev, name }))`.

### Когда это проявляется

При обычных кликах потерю не увидеть: каждый клик отдельное событие, после него следует рендер, и следующий обработчик
получает свежий снимок. Устаревший снимок появляется там, где:

- несколько `setState` подряд в **одном** блоке;
- `setTimeout`, `fetch().then`, `setInterval`, подписки: замыкание создано давно и держит старый снимок;
- эффекты и колбэки, захватившие состояние при создании.

Эксперимент: нажмите «+1 (async)» (таймер на 2 секунды) и сразу несколько раз «+1 (правильно)». Через 2 секунды таймер сделает
`setCount(0 + 1)` со старым снимком, и счётчик упадёт обратно. Пять кликов потеряны. С `prev => prev + 1` не потерялись бы.

### Когда апдейтер нужен, а когда нет

- **Не нужен**, если новое значение не зависит от прежнего: `setName(e.target.value)` для строки, `setOpen(false)`.
- **Нужен**, если результат считается из прежнего: `count + 1`, `!flag`, добавление в массив, любой `{ ...obj, поле }`.

Для объектного состояния удобно всегда писать апдейтер. Когда формулы разрастутся, следующий шаг это `useReducer`:
редьюсер `(state, action) => newState` по определению чистая функция от прежнего состояния.

## Чистота апдейтера

Апдейтер выполняется **не там, где написан**, а позже, при рендере, и может выполниться **несколько раз**:

- в dev-режиме `<StrictMode>` вызывает его дважды намеренно, чтобы вскрыть нечистоту;
- в конкурентном рендеринге React может отбросить и повторить рендер;
- иногда React выполняет его сразу при вызове `setState` (оптимизация, когда очередь пуста).

Поэтому апдейтер должен быть **детерминированным** (одинаковые `prev` и аргументы дают одинаковый результат) и **без
побочных эффектов**. Что из этого следует:

| откуда значение | где читать | почему |
|---|---|---|
| прежнее состояние | внутри, из `prev` | это работа апдейтера |
| `e.target.value`, `ref.current` | снаружи, в `const` | к рендеру значение уже изменилось (поле очищено) |
| `Date.now()`, `Math.random()`, `crypto.randomUUID()` | снаружи | при повторном вызове даст другой результат |

```ts
function handleAddTask() {
  const input = inputRef.current;
  if (!input) return;
  const title = input.value.trim();   // зафиксировали значение ДО апдейтера
  if (!title) return;
  const id = Date.now();

  setProject((prev) => ({ ...prev, tasks: [...prev.tasks, { id, title, done: false }] }));
  input.value = "";
}
```

Если читать `inputRef.current.value` внутри апдейтера, к моменту его выполнения поле уже очищено (`input.value = ""` отработало
синхронно), и задача добавится с пустым названием. Это похоже на отложенное выполнение в LINQ: `ref.current` изменяемая
«коробка», и замыкание хранит её, а не её содержимое на момент записи.

Мутация `prev` внутри апдейтера ломается вдвойне:

```ts
setProject(prev => { prev.tasks.push(x); return { ...prev }; });  // в StrictMode задача добавится ДВАЖДЫ
```

## Как React решает, перерисовывать ли компонент: Object.is

React сравнивает старое и новое состояние через `Object.is(old, new)`. Если результат `true`, перерисовки нет.
Примитивы сравниваются по значению, объекты и массивы по ссылке. Отсюда главное правило React:

> Не изменяйте состояние на месте. Создавайте новый объект/массив.

```ts
const [cart, setCart] = useState({ items: [], total: 0 });

cart.total = 100;   // мутация: ссылка та же
setCart(cart);      // Object.is(old, new) === true → перерисовки НЕТ
```

Что при этом происходит на самом деле: объект в памяти уже изменён (`cart.total === 100`), но интерфейс не обновился. Любой
следующий рендер (изменилось другое состояние, перерисовался родитель) прочитает изменённый объект, и значение
неожиданно «проснётся» на экране. Состояние и UI разошлись, а потом «магически» сошлись.

JavaScript и TypeScript мутацию не запрещают. Предупреждает об этом только ESLint-правило `react-hooks/immutability`
(плагин `eslint-plugin-react-hooks` v7, построен на статическом анализе React Compiler), и только там, где умеет
распознать (прямую запись в поле значения из `useState` оно поймает, а `task.done = ...` для найденного в массиве элемента не поймало).

## Иммутабельное обновление вложенного состояния

Оператор spread (`...`) делает **поверхностную** копию: копируются значения полей верхнего уровня, а для объектов и массивов значение это ссылка.

```ts
setProject(prev => ({ ...prev, tasks: newTasks }));
// новый объект project; name скопировано, owner и tasks указывают на те же объекты, что и раньше
```

Правило: **копируйте всё вдоль пути изменения**, остальное оставляйте общим (structural sharing).

```ts
// переключить done у одной задачи: копируем project → tasks → одну задачу
setProject(prev => ({
  ...prev,
  tasks: prev.tasks.map(t => (t.id === id ? { ...t, done: !t.done } : t)),
}));

// добавить:  [...prev.tasks, newTask]
// удалить:   prev.tasks.filter(t => t.id !== id)
// вложенный объект: { ...prev.owner, email: value }
```

Зачем это нужно кроме перерисовки: `React.memo`, `useMemo`, `useEffect`, `useCallback` сравнивают пропсы и зависимости по
`Object.is`. Если мутировать вложенный объект (`task.done = true`) и передать тот же `task` в `<TaskRow task={task} />`,
ссылка пропса не изменилась, и `memo` пропустит рендер: интерфейс остаётся старым. Неизменённые элементы должны сохранять
прежнюю ссылку, тогда `memo` для них работает.

## Батчинг (Automatic Batching)

https://dev.to/shivamjjha/batching-in-react-4pp3

React не рендерит сразу при каждом `setState`. Он ждёт, пока закончится текущий синхронный блок кода, и потом делает
**один** проход по накопленным очередям. Дело не в количестве обновлений, а в **моменте**.

Как это устроено:

1. Первый `setState` помечает компонент «нужен рендер» и планирует его.
2. Следующие `setState` в том же блоке видят, что рендер уже запланирован, и только добавляют записи в очередь.
3. Когда блок закончился, происходит один рендер, и все очереди применяются разом.

```ts
function handleClick() {
  setA(1);
  setB(2);
  setC(3);
  console.log("handler end");
  // порядок в консоли: "handler end", затем ОДИН "render"
}
```

Версии:

| | обработчик клика | `setTimeout`, `Promise.then`, `fetch` |
|---|---|---|
| React 17 | один рендер | рендер на **каждый** `setState` |
| React 18+ (`createRoot`) | один рендер | группируются (automatic batching) |

Гарантия действует для **одного синхронного блока**. Три отдельных `setTimeout` на одно время это три разные задачи цикла
событий, склеит ли их React в один рендер, зависит от тайминга. Итоговое значение от этого не зависит: `+1` даёт снимок,
а не количество рендеров.

Важно не путать два механизма: **снимок** определяет итоговое значение (`+1` против `+3`), **батчинг** определяет, сколько
раз отрисуется компонент.

`setState` не является асинхронной функцией (не возвращает `Promise`): он **откладывает** обработку. Состояние
в переменной не меняется и после рендера, меняется только то, что увидит следующий вызов компонента.

Отказаться от батчинга можно через `flushSync`: рендер происходит синхронно, прямо на этой строке (нужен редко,
например чтобы сразу прочитать DOM после обновления).

```ts
import { flushSync } from "react-dom";

function handle() {
  flushSync(() => setCount(c => c + 1)); // рендер сразу
  setOther(o => o + 1);                  // второй рендер в конце обработчика
  console.log("handler end");
  // порядок: render, handler end, render
}
```
