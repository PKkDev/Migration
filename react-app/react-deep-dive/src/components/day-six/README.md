# День 6. `useContext`: передача данных через дерево

## Зачем контекст

**Prop drilling**: данные нужны компоненту на 4-м уровне вложенности, и каждый промежуточный компонент вынужден принимать
и передавать проп, который сам не использует. Если у `Avatar` появляется новый проп (например `onLogout`), правки нужны в `Avatar`,
`UserMenu`, `Toolbar` и `Page`. Добавить поле в тип `User` при этом достаточно в одном месте. Боль начинается именно с новых пропсов
и колбэков. Контекст доставляет значение вниз, минуя посредников. Аналог в Angular: DI-провайдер; в .NET: `IServiceProvider`.

Контекст:
- **не хранит** состояние (оно лежит в `useState` провайдера), он только доставляет значение;
- **не замена менеджеру состояния** (Zustand/Redux, Дни 25–28) и не замена пропсам вообще;
- хорошо подходит для данных, которые меняются редко: тема, язык, текущий пользователь.

## Три шага

```tsx
const ThemeContext = createContext<Theme>("light");   // 1. создать, с значением по умолчанию
<ThemeContext value={theme}>…</ThemeContext>          // 2. предоставить поддереву (React 19: без .Provider)
const theme = useContext(ThemeContext);               // 3. прочитать в любом потомке
```

Потребитель получает значение от **ближайшего** провайдера над ним. Если провайдера нет, он получает **значение по умолчанию**,
переданное в `createContext` (у `createContext<T | null>(null)` это `null`, у `createContext("light")` это `"light"`).

## Хук-обёртка с проверкой провайдера

```ts
export class MissingContextError extends Error {
  constructor(hook: string, provider: string) {
    super(`${hook} must be used within <${provider}>`);
    this.name = "MissingContextError";
  }
}

export const useAuth = (): AuthContextValue => {
  const ctx = useContext(AuthContext);
  if (ctx === null) throw new MissingContextError("useAuth", "AuthProvider");
  return ctx;                       // тип сужен: потребителям не нужен ?.
};
```

Зачем:
1. Проверка в **одном** месте, а не в каждом компоненте.
2. Хук **сужает тип** до не-null, потребителям не нужны `?.` и проверки.
3. Ошибка называет, что забыли (`useAuth must be used within <AuthProvider>`). `useContext(...)!` лишь заглушает компилятор,
   при забытом провайдере вы получите непонятный `TypeError` где-то глубже.
4. Компоненты не импортируют сам контекст, только хук.

Файлы раскладывают по трём, чтобы не нарушить `react-refresh/only-export-components`: `XContext.ts` (контекст и тип),
`XProvider.tsx` (компонент), `useX.ts` (хук). Общий класс ошибки лежит отдельно.

Проверка: убрать провайдер, и ошибка должна прийти в `errorElement` роутера. Чтобы показать сообщение, а не статический текст,
в `errorElement` используют `useRouteError()` (по желанию с проверкой `instanceof MissingContextError`).

## Каскадные перерисовки

Когда `value` провайдера изменился (сравнение `Object.is`, ссылочное), React перерисовывает **всех** потребителей контекста,
даже тех, кто читает только одно поле. Объект в `value={{...}}` создаётся **заново при каждом рендере провайдера**, поэтому
`Object.is` почти всегда даёт `false`.

`React.memo` не помогает от смены контекста: он сравнивает **пропсы**, а подписка на контекст идёт отдельным каналом.
`memo` защищает от перерисовки родителя, но не от изменения `value`.

Провайдер с собственным состоянием и `{children}` перерисовывает своё поддерево избирательно: `children` приходят от
родителя, это те же элементы, поэтому React их не перерисовывает, кроме потребителей изменившегося контекста.

### Три способа и их цена

| способ | как помогает | цена |
|---|---|---|
| **Разделить контексты** по причинам изменения (`UserContext` + `NotifContext`) | потребитель подписан только на то, что читает: «+1 notif» не трогает компоненты, читающие пользователя | больше провайдеров и хуков; границу выбирают вручную; сам по себе не защищает от перерисовки родителя |
| **`useMemo` для `value` + `useCallback` для функций** | объект остаётся тем же, пока данные не изменились: защита от перерисовки провайдера по чужой причине | шум в коде; нужно следить за зависимостями; не помогает, если данные реально изменились |
| **Состояние ближе к потребителям / трюк с `children`** | провайдер перерисовывается реже, его `children` остаются теми же элементами | иногда нужно перестраивать дерево |

Разделение и `useMemo` решают **разные** проблемы:

| сценарий | базовый | + `memo` на потребителе | + `useMemo`/`useCallback` | разделение + `useMemo` |
|---|---|---|---|---|
| S1: изменилось поле A | все потребители | все (`memo` не помогает) | все | только читающие A |
| S2: изменилось поле B | все потребители | все | все | только читающие B |
| S3: провайдер перерисовался по чужой причине (родитель) | все | все | **никто** | **никто** |

### `useMemo` и `useCallback`

```tsx
const update = useCallback(() => setCount((prev) => prev + 1), []);          // функция: сеттер стабилен, deps пустые
const value = useMemo(() => ({ count, update }), [count, update]);           // объект: пересчёт только при смене данных
```

- `useMemo(fn, deps)` хранит результат вычисления и возвращает **ту же ссылку**, пока зависимости (по `Object.is`) те же.
- `useCallback(fn, deps)` то же самое для функции, то есть `useMemo(() => fn, deps)`. Без него функции в `value` были бы новыми каждый рендер,
  и `useMemo` не имел бы смысла.
- Хуки нужны, только если провайдер может перерисоваться **без изменения данных** (перерисовался родитель). Если провайдер стоит
  в корне, а корень сам почти не перерисовывается, толку нет. Нужно мерить Profiler'ом, а не оптимизировать «на всякий случай».
  React Compiler (если включён) делает такую мемоизацию автоматически.

## `use(Context)` в React 19

`use(Context)` читает то же значение, что и `useContext`, и подписка работает так же. Отличия:
1. `use` можно вызывать **условно**: после раннего `return`, внутри `if`, в цикле. `useContext` как хук нельзя (правила хуков, День 7).
2. `use` умеет ещё и читать промисы (с `Suspense`, День 20+).

```tsx
function Panel({ open }: { open: boolean }) {
  if (!open) return null;
  const theme = use(ThemeContext);   // допустимо; useContext здесь нарушил бы правила хуков
  return <div className={theme}>…</div>;
}
```

## Состояние провайдера и навигация

Провайдер, стоящий в layout-маршруте (`App`) над `<Outlet />`, **не размонтируется** при переходе между страницами: меняется
только содержимое outlet'а. Поэтому состояние (залогиненный пользователь, счётчик) сохраняется при навигации. Оно живёт только
в памяти, поэтому F5 и новая вкладка начинают с начального значения. Для реальной авторизации токен хранят отдельно (Дни 43–44).
