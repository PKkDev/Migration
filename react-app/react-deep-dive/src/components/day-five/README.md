# День 5. Устаревшие замыкания (stale closures) и массив зависимостей

## Замыкание и React

Замыкание это функция плюс переменные из места, где она создана. Аналогия из C#: лямбда, захватившая локальную переменную.

Разница, которая всё объясняет. В C# лямбда захватывает **переменную** и увидит её изменения. В React каждый рендер это
новый вызов функции компонента, а значит **новый набор констант** (`count`, `props`). Значения не изменяются: в новом
рендере появляются новые константы. Функции, созданные в рендере (обработчик, колбэк эффекта, колбэк `setInterval`),
навсегда привязаны к **значениям этого рендера**. Это тот же снимок (snapshot) из Дня 2.

Пока функция живёт один рендер (обработчик клика), проблемы нет. Она появляется, когда функция **живёт дольше одного
рендера**: колбэк `setInterval`/`setTimeout`, подписка, `.then()` у запроса. Такая функция видит значения того рендера, где
её создали. Это и есть **stale closure**.

## Классическая ловушка

```tsx
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);   // count из первого рендера (0)
  return () => clearInterval(id);
}, []);                                                        // эффект создан один раз
```

Эффект выполнился один раз, колбэк навсегда видит `count = 0` и каждый тик делает `setCount(0 + 1)`. React сравнивает
`Object.is(1, 1)` и ничего не перерисовывает, счётчик стоит на 1. Если нажать `+10`, на следующем тике значение вернётся
на 1: это самое наглядное проявление проблемы.

Пример на другой предметной области: опрос комнаты чата.

```tsx
useEffect(() => {
  const id = setInterval(() => console.log("опрашиваем", roomId), 5000);
  return () => clearInterval(id);
}, []);   // roomId сменился, а интервал по-прежнему опрашивает первую комнату
```

## Два дефекта, которые нужно различать

| дефект | признак | исправление |
|---|---|---|
| **нет cleanup** | интервалы копятся (без массива или с `[count]`), в StrictMode пара `tick` на каждую секунду | `return () => clearInterval(id)` |
| **ложный массив зависимостей** | колбэк видит устаревшее значение | один из способов ниже |

Убирание массива зависимостей лечит только симптом: интервалы множатся, настоящая проблема (нет cleanup) остаётся.

## Что обещает массив зависимостей

Массив это обещание React: «эффект использует **только** эти значения из компонента. Когда они изменятся, перезапусти меня
(cleanup → setup), чтобы замыкание получило свежие значения».

- **Если соврать** (не указать то, что эффект читает), эффект **не перезапускается, когда должен**, и внутри остаются
  устаревшие значения. Лишних вызовов нет, не хватает нужных. Так возник баг.
- `react-hooks/exhaustive-deps` ловит значения из компонента (состояние, пропсы, функции), которые эффект использует, но
  которых нет в массиве. Правило не отключают, а исправляют код.
- Сообщение линтера бывает подсказкой: «You can also do a functional update `setCount(c => ...)`».

## Способы лечения

| способ | идея | цена |
|---|---|---|
| **Функциональный апдейтер** `setCount(prev => prev + 1)` | колбэк не читает `count`, зависимость исчезает; `prev` подставляет сам React из очереди (День 2) | значение нельзя прочитать (лог, условие), только преобразовать |
| **Честная зависимость** `[count]` | эффект перезапускается при каждом изменении: cleanup → setup | интервал пересоздаётся каждый тик; «+10» посреди секунды **сбрасывает** отсчёт; ритм нарушается |
| **Latest ref** (зеркало состояния) | долгоживущая функция читает свежее значение из `ref.current` | лишняя коробка; правила ref (читать только в обработчиках и эффектах) |
| **`useEffectEvent`** (React 19.2+) | функция внутри эффекта, всегда видящая свежие значения, но не являющаяся зависимостью | вызывать можно только из эффекта; нужно понимать «нереактивную» часть |

Порядок выбора: сначала апдейтер, затем честные зависимости (если пересоздание допустимо), затем latest ref или
`useEffectEvent` для оставшихся случаев, когда значение нужно **прочитать**.

`[]` не способ починки, а исходная ошибка.

Вариант `[count]` допустим, когда пересоздание эффекта безвредно: например, подписка на запрос по `id` (так и должно быть,
День 4). Для периодического «тика» он плох, потому что тик зависит от обновлений состояния.

## Latest ref: зеркало, а не второй источник

```tsx
const [unread, setUnread] = useState(0);
const unreadRef = useRef(unread);
useEffect(() => { unreadRef.current = unread; });     // зеркало: после каждого рендера

useEffect(() => {
  const id = setInterval(() => report(unreadRef.current), 5000);   // свежее значение, эффект с []
  return () => clearInterval(id);
}, []);
```

Ref **повторяет** состояние после каждого рендера (как `usePrevious` из Дня 3), а не живёт параллельно. Если обновлять ref
руками рядом с каждым `setCount`, получатся два источника истины, и они разойдутся при первой новой точке, где
кто-то вызовет `setCount` и забудет ref.

## Alert через 3 секунды: это не баг

```tsx
function showLater() { setTimeout(() => alert(count), 3000); }
```

`count` это константа **рендера, в котором нажали кнопку**, то есть число, которое пользователь видел на экране в момент
клика. Пока идёт таймер, состояние меняется, но замыкание о нём не знает. Это снимок (День 2): React показывает то, что было
видно в момент действия. Если нужно «последнее значение», читают `ref.current` (зеркало).

Дополнительно: таймер из обработчика тоже нужно останавливать при размонтировании, если по его завершении трогается UI
(`setTimeout` без cleanup: уйти со страницы за 3 секунды, а алерт всё равно появится).

## Роутинг как инструмент проверки

После каркаса навигации (React Router, Data mode) каждый день живёт на своей странице. Переход на другую страницу
**размонтирует** компонент и запускает cleanup эффектов. Это удобный способ проверить, что интервалы и подписки
останавливаются: запустить, уйти на другую страницу и посмотреть консоль.
