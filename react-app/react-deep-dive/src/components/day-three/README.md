# День 3. `useRef`: выход за пределы цикла рендеринга

## Ref это коробка, которая переживает рендеры

Локальные переменные сбрасываются при каждом вызове компонента, состояние переживает рендеры, но каждое его изменение
вызывает перерисовку. Нужен третий вариант: хранилище, которое **переживает рендеры и не вызывает перерисовку**.

```tsx
const ref = useRef(0);   // → { current: 0 }
```

- Объект `{ current }` создаётся **один раз** при первом рендере и дальше возвращается тот же самый (стабильная ссылка).
- Запись `ref.current = 5` ничего не планирует: нет очереди, нет рендера.
- Документация описывает это так: `useRef` это `useState({ current: init })[0]` без сеттера.

Аналогия из C#: локальная переменная метода это `let` в теле компонента, а ref это **поле экземпляра** (`this._timerId`).

## `useState` против `useRef`

| | `useState` | `useRef` |
|---|---|---|
| Переживает рендеры | да | да |
| Изменение вызывает рендер | **да** | **нет** |
| Менять напрямую | нет (только через setter) | да, `ref.current = ...` |
| Читать в теле компонента (при рендере) | можно | **нельзя** |

Критерий выбора: **если значение участвует в JSX, это состояние. Если нет, это ref** (id таймера, DOM-узел, предыдущее
значение, флаг «уже отправлено»). Пример из практики: секунды секундомера состояние, id его интервала ref.

## Главное правило: не читайте и не пишите `ref.current` во время рендера

«Во время рендера» значит: то, что выполняется, когда React вызывает функцию компонента (тело компонента, JSX-выражения,
тела хуков). Объявление функции-обработчика внутри компонента рендером не является: сама функция выполнится позже, при событии.

| где выполняется код | читать и писать `ref.current` |
|---|---|
| тело компонента, JSX, тело хука | **нельзя** |
| обработчик события (`onClick`, `onChange`) | можно |
| `useEffect` | можно |

Почему нельзя:

1. Рендер должен быть **чистым и повторяемым**: React вызывает функцию компонента повторно (StrictMode), может прервать рендер
   или отбросить его. Если результат зависит от ref, который меняют вне рендера, повторные вызовы дают разные результаты.
2. **React Compiler** запоминает результат компонента по состоянию и пропсам. Изменение ref он не отслеживает, и компонент
   может не обновиться, хотя в ref уже новое значение.

Единственное допустимое исключение: ленивая инициализация («если пусто, создать»):

```ts
if (!itemsRef.current) itemsRef.current = new Map();
```

Правило проверяет ESLint (`react-hooks/refs`, плагин `eslint-plugin-react-hooks` v7):
`Cannot access refs during render`.

## Ref на DOM-узел

Атрибут `ref` на JSX-элементе говорит React: «когда создашь настоящий узел, положи его сюда».

```tsx
const inputRef = useRef<HTMLInputElement>(null);
<input ref={inputRef} />
```

- `inputRef.current === null`: во время **первого рендера** (узла ещё нет) и после размонтирования;
- `inputRef.current === <input>`: между монтированием и размонтированием.

Объект `inputRef` создан сразу (с `null` внутри), а `current` заполняется на этапе **commit**, когда DOM уже создан.
Поэтому `console.log(inputRef.current)` в теле компонента печатает `null` при первом рендере и сам элемент при следующих.

Работать с DOM-узлом нужно в обработчиках и эффектах (`inputRef.current?.focus()`).
Аналог в Angular: `@ViewChild` + `ElementRef`.

## Ref в списке: Map и callback ref

Хук нельзя вызвать для каждой строки в `map`: React определяет хук **по порядку вызова** (Rules of Hooks), а длина списка
меняется. Решение: один ref с `Map<id, узел>` и функция в `ref`:

```tsx
const itemsRef = useRef<Map<number, HTMLDivElement>>(null);
function getMap() {
  if (!itemsRef.current) itemsRef.current = new Map();   // ленивая инициализация
  return itemsRef.current;
}

{messages.map((m) => (
  <div
    key={m.id}
    ref={(node) => {
      const map = getMap();
      map.set(m.id, node);
      return () => { map.delete(m.id); };               // cleanup (React 19)
    }}
  />
))}
```

- Ключом `Map` берите стабильный идентификатор (`id`), а не объект сообщения: при иммутабельном обновлении объект будет другим.
- Функция из `ref` вызывается при монтировании (получает узел). В **React 19**, если она возвращает функцию очистки,
  при размонтировании вызывается cleanup, а вызова с `null` уже нет.
- Функция в `ref={(node) => ...}` создаётся заново **на каждом рендере**, поэтому React на каждом рендере вызывает старый
  cleanup и новую функцию для каждой строки. Для сотен строк это незаметно, для тысяч стоит делать стабильную функцию
  (вынести строку в отдельный компонент).
- `scrollIntoView` прокручивает все прокручиваемые предки (включая страницу). Для вертикального списка `inline` не нужен.

В React 19 `ref` в функциональных компонентах это обычный проп, `forwardRef` для новых компонентов не нужен.

## Секундомер: id интервала в ref

```tsx
const intervalRef = useRef<number | null>(null);

function start() {
  if (intervalRef.current != null) return;               // защита от двойного старта
  intervalRef.current = window.setInterval(() => setSeconds((p) => p + 1), 1000);
}
function stop() {
  if (intervalRef.current != null) {
    clearInterval(intervalRef.current);
    intervalRef.current = null;
  }
}
```

Что ломается при других способах хранения:

- **Локальная переменная `let`**: у каждого рендера своя переменная, секундомер перерисовывается раз в секунду, поэтому
  `stop` видит `null` и ничего не останавливает, а `start` можно нажать повторно. Линтер (`react-hooks/immutability`) тоже ругается.
- **Состояние**: id на экране не виден, поэтому лишние рендеры на Start и Stop бессмысленны.
  Хуже: `setIntervalId(() => setInterval(...))` создаёт интервал **внутри апдейтера**. Апдейтер должен быть чистым (День 2),
  StrictMode вызывает его дважды, получается два интервала на один Start, а id сохраняется только одного.
- Правильно: создавать интервал **снаружи** (`const id = setInterval(...)`), а в состояние или ref класть уже готовый id.

**Утечка:** если скрыть компонент (`{show && <Stopwatch />}`), интервал продолжает работать, потому что компонент не вызывает
`clearInterval` при размонтировании. Исправление через cleanup в `useEffect` (День 4).

## `usePrevious`: ref и эффект

```ts
export function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T | undefined>(undefined);
  useEffect(() => { ref.current = value; });   // после КАЖДОГО рендера
  return ref.current;                          // во время рендера: значение, записанное после прошлого
}
```

Порядок в каждом рендере: **(1)** во время рендера хук возвращает то, что лежит в ref, **(2)** React обновляет DOM,
**(3)** эффект записывает в ref значение **этого** рендера.

| событие | рендер | `price` | хук вернёт | эффект запишет |
|---|---|---|---|---|
| старт | 1 | 0 | `undefined` | 0 |
| «+10» | 2 | 10 | **0** | 10 |
| посторонний клик | 3 | 10 | **10** | 10 |

Хук помнит значение **предыдущего рендера**, а не **предыдущего изменения**. Посторонний клик тоже даёт рендер, эффект
перезаписывает ref, и «предыдущее» становится равным текущему.

Чтобы получить «предыдущее изменение»: обновлять запись «предыдущее» только если значение изменилось (хранить «текущее» и
«предыдущее» отдельно) или хранить предыдущее в состоянии и обновлять его в обработчике, там, где цена реально меняется.

Чтение `ref.current` в теле хука нарушает правило `react-hooks/refs`. Для учебного примера его подавляют осознанно,
с комментарием. В реальном коде значение, которое нужно для отрисовки, лучше хранить в состоянии
([Storing information from previous renders](https://react.dev/reference/react/useState#storing-information-from-previous-renders)).
Ref подходит, если «предыдущее» нужно только в эффекте или обработчике (логирование, аналитика).

**Производное состояние:** если значение можно вычислить из другого состояния (`futurePrice` всегда равно `price` после
рендера), второго состояния заводить не нужно.

## Сколько элементов выдержит список

Перерисовка компонента с `messages.map(...)` создаёт описание для каждого элемента и сравнивает деревья: это O(n) JS-работы,
а в DOM меняется только отличающееся. Для сотен элементов это незаметно, около 10 000 уже ощутимо, а миллионы узлов
в DOM не потянет браузер независимо от React. Решения: виртуализация (в DOM только видимые строки, День 39–40),
пагинация, вынос часто меняющегося состояния в отдельный компонент, `React.memo` на строках, `useDeferredValue`/`useTransition`.
Сначала измерять Profiler'ом. С виртуализацией `Map` с DOM-узлами перестаёт работать для невидимых строк, нужен `scrollToIndex`.
