# День 4. `useEffect`: модель синхронизации и StrictMode

## Эффект это не `ngOnInit`

Рендер должен быть чистым: он только вычисляет картинку из состояния и пропсов (Day 2–3). Но иногда компоненту нужно общаться
с **внешним миром, которым React не управляет**: подписка на события окна, таймер, сетевой запрос, DOM API, сторонний виджет.
Для этого и есть эффект:

> Эффект синхронизирует компонент с внешней системой.

Мысль не «что произойдёт при монтировании», а «что нужно **запустить** и как это **остановить**». Поэтому `ngOnInit`/`ngOnDestroy`
и `Form_Load` плохие аналоги: эффект привязан не к жизненному циклу компонента, а к паре «начать синхронизацию, закончить».

## Устройство

```tsx
useEffect(() => {
  // setup: начать синхронизацию (подписаться, запустить, подключиться)
  return () => {
    // cleanup: остановить ту же синхронизацию (отписаться, остановить, отключиться)
  };
}, [dep1, dep2]);
```

Эффект выполняется **после** того, как React обновил DOM (после commit, Day 3), а не во время рендера. Поэтому в нём можно
читать ref и работать с DOM.

Когда выполняется setup:

| массив зависимостей | когда |
|---|---|
| `[]` | после первого показа компонента; cleanup при исчезновении |
| `[a, b]` | после первого показа и после каждого рендера, где `a` или `b` изменились (сравнение `Object.is`, Day 2) |
| не указан | после **каждого** рендера |

Порядок вызовов:

| момент | что происходит |
|---|---|
| первый показ | setup |
| изменилась зависимость | **cleanup старого запуска, затем setup нового** |
| размонтирование | cleanup |

Cleanup всегда относится к **старому** запуску и видит значения прежнего рендера. Например, при переходе с `id=1` на `id=2`
в `UserCard` сначала срабатывает cleanup (отмена запроса для 1), потом setup (запрос для 2).

## StrictMode: setup → cleanup → setup

В `main.tsx` обёртка `<StrictMode>`. В dev-режиме React **намеренно имитирует** размонтирование и повторное монтирование:
для каждого эффекта выполняется цепочка **setup → cleanup → setup**. Это не баг и не двойной монтаж компонента, и в
production так не происходит.

Цель: проверить, что cleanup **полностью отменяет** setup. Критерий корректности: после «setup → cleanup → setup»
приложение ведёт себя так же, как после одного setup: один слушатель, один интервал, один запрос. Забытый cleanup в dev виден сразу
(например, обработчик `resize` срабатывает дважды на одно событие).

## Зависимости не выбирают, их считают

Всё, что эффект использует из компонента (состояние, пропсы, функции), должно быть в массиве. Это проверяет правило
`react-hooks/exhaustive-deps`. Если зависимость «мешает», её не убирают из массива, а перестраивают код (Day 5).

## Подписка с cleanup

```tsx
useEffect(() => {
  const handleResize = () => {          // обработчик внутри эффекта: одна и та же ссылка для add и remove
    setWidth(window.innerWidth);
    setHeight(window.innerHeight);
  };
  window.addEventListener("resize", handleResize);
  return () => window.removeEventListener("resize", handleResize);
}, []);
```

Без `removeEventListener` слушатель остаётся жить после размонтирования: в dev из-за StrictMode на одно событие
сработают два обработчика, а при каждом повторном показе компонента подписок станет ещё больше.

## Запрос данных: гонка и `AbortController`

**Гонка запросов:** ответы приходят в другом порядке, чем уходили запросы. Ответ на устаревший запрос пришёл позже нового и
перезаписал состояние, и на экране данные не для текущего id.

Решение: при смене зависимости **отменить** прежний запрос в cleanup.

```ts
useEffect(() => {
  const controller = new AbortController();
  fetch(url, { signal: controller.signal });
  return () => controller.abort();      // fetch завершится ошибкой AbortError
}, [id]);
```

`AbortError` нужно **игнорировать** в `catch` (отмена это нормальная часть работы cleanup, а не ошибка пользователю).

Важно:

- `fetch` **не** бросает ошибку на 404 и 500: нужно проверять `response.ok`. Axios (используется в `UserCard`) бросает сам.
- Если состояние «загрузка» и «ошибка» можно **вывести** из других данных, не заводите для них отдельные состояния и не вызывайте
  `setState` в теле эффекта (правило `react-hooks/set-state-in-effect`: лишний рендер сразу после эффекта).
  В `UserCard`: данные и ошибка хранятся вместе с `id` запроса, а «загрузка» это `!currentUser && !currentError`.
- В реальных проектах загрузку данных делают через TanStack Query (Дни 15–18): там отмена, кэш и гонки решены.

## Что эффектом делать не нужно

Из «You Might Not Need an Effect»:

| задача | вместо эффекта |
|---|---|
| значение из состояния или пропсов | вычислить прямо в теле компонента (если дорого, `useMemo`, День 11) |
| реакция на действие пользователя | обработчик события (`onClick` и т. п.) |
| сброс состояния при смене пропса | `key` на компоненте (День 9) или вычисление в рендере |
| цепочки «эффект меняет состояние, другой эффект на него реагирует» | пересчитать всё в одном месте (обработчик или рендер) |
