# День 7. Кастомные хуки и правила хуков

## Кастомный хук: общий код, не общее состояние

Кастомный хук это функция с именем `useX`, которая внутри вызывает другие хуки. Он делит между компонентами **логику**, а не
**состояние**: каждый вызов получает свою копию состояния.

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = () => setOn((p) => !p);
  return [on, toggle] as const;
}
function Menu()    { const [open, toggle] = useToggle(); … }   // свой `open`
function Tooltip() { const [open, toggle] = useToggle(); … }   // свой, независимый `open`
```

Хук не отдельный компонент и не отдельный рендер: его хуки встраиваются в тело вызывающего компонента. У `SearchPosts`
один плоский список хуков: `useState` постов и статуса, `useState` и `useCallback` из `useLocalStorage`, `useState` и
`useEffect` из `useDebounce`, свой `useEffect` запроса. Логи `useDebounce render` и `SearchPosts render` это **один и тот же**
рендер.

Чтобы состояние **делилось**, нужен контекст (День 6) или внешний стор (Дни 25–28).

Когда выносить в хук: логика использует хуки (иначе достаточно обычной функции) и повторяется или имеет понятное назначение
(`useDebounce`, `useOnlineStatus`). Не стоит делать обёртки `useMount`/`useUpdate`: они прячут модель эффектов (День 4).
Возвращаемое значение: кортеж `[value, setValue]`, если значений два (как `useState`), объект, если больше.

Аналоги из Angular: `useDebounce` ≈ `valueChanges.pipe(debounceTime(...))`, эффект с `AbortController` ≈ `switchMap`,
который отписывается от прошлого запроса.

## Правила хуков

1. Хуки вызываются только **на верхнем уровне** компонента или хука: не в `if`, цикле, вложенной функции, обработчике,
   после раннего `return`, не в `try/catch`.
2. Хуки вызываются только из **компонентов** и **кастомных хуков** (имя начинается с `use`).

Почему: у хука нет имени, React идентифицирует его **по порядку вызова**. Для компонента хранится список слотов
(слот 1, слот 2, …), и n-й вызов хука получает n-й слот. Если порядок или число вызовов меняется между рендерами,
значения «съезжают».

```tsx
function CustomerCard({ vip }: { vip: boolean }) {
  const [open, setOpen] = useState(false);        // слот 1
  if (vip) { const [badge, setBadge] = useState("gold"); }   // слот 2 только при vip — нарушение
  const [note, setNote] = useState("");           // слот 3, а при vip=false получит слот 2 со значением "gold"
}
```

| нарушение | что ломается |
|---|---|
| хук в `if` | число и порядок вызовов зависят от условия |
| хук в цикле / `.map` | число хуков зависит от длины списка (поэтому в Дне 3 `Map` на весь список, а не хук на строку) |
| хук после раннего `return` | при срабатывании `return` часть хуков не вызывается («Rendered fewer hooks than expected») |
| хук в обработчике | вызывается не в рендере, слот определить нельзя |
| хук в обычной функции | у неё нет своего списка слотов |

Как делать условно: условие **внутри** хука (`useEffect(() => { if (vip) … }, [vip])`) или условная часть выносится в
отдельный компонент (`{vip && <VipBadge />}`), у которого свой список слотов.

`use(Context)` (День 6) вызывается условно, потому что читает значение напрямую, а не берёт слот по порядку.

Линтер (`react-hooks/rules-of-hooks`) ловит нарушения до запуска; префикс `use` нужен ему и React, чтобы применить правила
к функции.

## `useDebounce`: отложить, пока не затихло

Debounce: действие выполняется, когда ввод прекратился на заданное время; каждое новое событие сбрасывает таймер.
Throttle: пропускает не чаще одного раза за интервал и срабатывает регулярно во время непрерывного ввода.

```ts
function useDebounce<T>(value: T, delay: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);          // новое значение или размонтирование: прошлый таймер отменяется
  }, [value, delay]);
  return debounced;
}
```

- Cleanup отменяет **таймер**: без него каждый символ дал бы свой `setDebounced`, и срабатывали бы все таймеры подряд.
- Зависимости `[value, delay]`: эффект использует оба.
- `setDebounced` вызывается в колбэке таймера (асинхронно), поэтому `react-hooks/set-state-in-effect` не срабатывает.

## `useLocalStorage`: синхронизация с внешней системой

| задача | как |
|---|---|
| прочитать при старте | **ленивая инициализация** `useState(() => read())`: значение известно в первом рендере, без лишнего рендера и без `setState` в эффекте |
| ключа нет | `initialValue` |
| битый JSON, недоступное или переполненное хранилище | `try/catch`, не падать, вернуть `initialValue` |
| записать | сеттер: `setValue(next)` + `localStorage.setItem(key, JSON.stringify(next))` внутри `useCallback(..., [key])` |

`useCallback` с `[key]` делает сеттер **стабильным**: без него `save` это новая функция на каждый рендер, и эффект, который
её использует, перезапускается постоянно (и линтер требует её в зависимостях). Так `save` честно попадает в `[debounced, save]`.

Сериализация через JSON: `Date`, `Map`, `undefined` теряются. Бонус: событие `storage` для синхронизации между вкладками;
«правильный» инструмент для внешних хранилищ `useSyncExternalStore`.

## Паттерны для хранимого значения

| значение | паттерн |
|---|---|
| короткое (строка поиска), запись при каждом символе дёшева | поле живёт на хуке: `const [q, setQ] = useLocalStorage(...)`, `<input value={q} onChange={...}>`; **один источник правды** |
| большое (текст), писать на каждый символ дорого | локальное `useState` (стартует с сохранённого), в хранилище пишем уже `debounced` эффектом `[debounced, save]` |

Признак неверной схемы: приходится городить `isFirstRender`, `ref` на поле ввода, добавлять в зависимости лишнее ради линтера.
Нужно найти единственный источник значения и дать эффекту только его реальные входы.

## Поиск с отложенным вводом

```
ввод символа → setSearchPart (хук: состояние + localStorage) → рендер, поле показывает значение
            → useDebounce ждёт паузу → debounced изменился
            → эффект запроса (единственная зависимость: debounced)
            → axios + AbortController; cleanup отменяет прошлый запрос
```

- Эффект запроса читает только `debounced`, его в зависимостях и указывают. Пока набирается слово, эффект **не запускается**
  (его зависимость не меняется), а перерисовывается компонент на каждый символ.
- debounce уменьшает **число** запросов, `AbortController` отменяет **устаревший** запрос и решает гонку ответов. Нужны оба.
- При F5 `debounced` стартует равным сохранённому значению: первый запрос уходит без паузы. В dev из-за StrictMode это
  `setup → cleanup → setup`.
- Запрос кодируется через `params: { q }` у axios, а не склейкой строки.

## Модель «двух часов» и чтение рендеров

| значение | когда меняется | от него зависит |
|---|---|---|
| `searchPart` | на каждый символ | поле ввода, запись в хранилище |
| `debounced` | после паузы | эффект запроса |

Три правила, из которых выводится всё:
1. Рендер чистый: считает картинку из `state` и `props`, значения внутри константы.
2. Меняется только через сеттер, он планирует новый вызов компонента.
3. Эффект запускается после рендера, если изменились его зависимости; cleanup отменяет прошлую синхронизацию.
