## Основы: классы и `Object`

- Любой класс неявно наследует `java.lang.Object` (как в C#). От него приходят `toString()`, `equals()`, `hashCode()`,
  `getClass()`.
- **Наследование классов одиночное** (`extends`), интерфейсов можно реализовать несколько (`implements`):
  `class Dog extends Animal implements Swimmer, Runner`. В C# запись через двоеточие: `class Dog : Animal, ISwimmer`.
- Интерфейсы в Java называют **без префикса `I`**: `Printable`, а не `IPrintable`.
- **Один публичный класс на файл**, имя файла совпадает с именем класса.
- **Свойств нет.** Поле делают `private`, а доступ дают методами `getName()` / `setName(...)`. Для неизменяемых данных
  берут `record` (методы доступа без `get`), для остального Lombok (`@Getter`, `@Setter`).

## Модификаторы доступа

| Java | Кто видит | Ближайший аналог в C# |
|---|---|---|
| `public` | все | `public` |
| `protected` | **тот же пакет** и наследники | `protected internal` (шире, чем C# `protected`) |
| *(без модификатора)* package-private | только тот же пакет | `internal` (но по пакету, а не по сборке) |
| `private` | только этот класс | `private` |

Главная ловушка: Java `protected` открывает член ещё и **всему пакету**, а C# `protected` только наследникам.
Модификатора для «видно всей сборке» нет: границей служит пакет (а в Java 9+ ещё и модуль).
Класс верхнего уровня может быть только `public` или package-private.

## Все методы виртуальные

В Java **нет ключевых слов `virtual` и `override`**: любой нестатический метод можно переопределить в наследнике.
Запретить это можно через `final`. Аннотация `@Override` не обязательна, но её ставят всегда: если сигнатура не
совпадёт с методом родителя (опечатка в имени, другой тип параметра), компилятор сообщит об ошибке, а не создаст
молча новый метод.

```java
abstract class Shape {
    public abstract double area();                    // нет реализации, обязаны переопределить
    @Override public String toString() { return getClass().getSimpleName() + " area=" + area(); }
}
class Circle extends Shape {
    private final double r;
    Circle(double r) { this.r = r; }
    @Override public double area() { return Math.PI * r * r; }
}

Shape s = new Circle(2);
s.area();        // вызовется Circle.area(): тип определяется по объекту, а не по переменной
```

Правила переопределения:

- нельзя **сузить доступ** (`public` метод родителя не сделать `protected`), можно расширить;
- **возвращаемый тип** можно сузить (ковариантность): метод родителя возвращает `Number`, а у наследника `Integer`;
- нельзя переопределить `final`, `private` и `static` методы. `static` метод в наследнике **скрывает** родительский
  (hiding), и выбирается он **по типу переменной**, а не по объекту;
- **поля не полиморфны**: поле с тем же именем в наследнике скрывает родительское, и доступ идёт по типу переменной.
  Проверено запуском: `Base b = new Child(); b.tag` возвращает поле `Base`, а `((Child) b).tag` поле `ChildT`;
- переопределение (override: та же сигнатура) это не перегрузка (overload: то же имя, другие параметры).

`super.method()` вызывает реализацию родителя (аналог `base.Method()`).

### По объекту или по типу переменной

Это главный вопрос полиморфизма. Для `ParentT p = new ChildT()` (переменная типа родителя, объект наследника):

| Что вызываем | Что выбирается | Результат (первые две строки это `task4`, статический вариант проверен отдельно) |
|---|---|---|
| обычный метод `p.say()` | **по объекту** (реальный тип `ChildT`) | `ChildT say` |
| поле `p.name` | **по типу переменной** (`ParentT`) | `ParentT` |
| статический метод `p.staticSay()` | **по типу переменной** (`ParentT`) | `ParentT say` |

Выводы:

- **методы экземпляра полиморфны**: вызов идёт к реализации того класса, чей объект на самом деле лежит в переменной;
- **поля и статические методы не полиморфны**: поле наследника с тем же именем только *скрывает* родительское, а
  статический метод наследника *скрывает* родительский (hiding). Выбор делает компилятор по объявленному типу
  переменной;
- поэтому **не давайте полям наследников те же имена, что у родителя** и не вызывайте статику через переменную
  (`p.staticSay()` вместо `ParentT.staticSay()`): IDE предупредит, и это путает читающего.

В C# с полями то же самое (поле-«тень» требует `new`), а статические методы вызываются только через имя класса.

## `final`

| Где | Что значит | Аналог в C# |
|---|---|---|
| поле | значение присваивается один раз (в объявлении или конструкторе) | `readonly` |
| локальная переменная, параметр | нельзя переприсвоить | (нет) |
| метод | нельзя переопределить | `sealed override` |
| класс | нельзя наследовать | `sealed` |

`final` у ссылки не делает объект неизменяемым: можно менять содержимое `final List`, нельзя присвоить ей другой список.

## Абстрактные классы и интерфейсы

**`abstract class`**: можно иметь поля, конструкторы и состояние, но нельзя создать экземпляр напрямую. Часть методов
могут быть `abstract` (без тела).

**`interface`**: контракт. Все члены по умолчанию `public`; поля неявно `public static final` (константы). Начиная с
Java 8 в интерфейсе могут быть:

- **`default`-методы** с реализацией (аналог default interface methods из C# 8);
- **`static`-методы**;
- **`private`-методы** (Java 9+): общие вспомогательные для default-методов.

```java
interface Printable {
    void print();                                         // обязателен
    default void printTwice() { print(); print(); }       // готовая реализация
}
```

**Конфликт default-методов (проблема ромба).** Если класс реализует два интерфейса с одноимённым default-методом,
компилятор требует явно переопределить его и выбрать нужную реализацию:

```java
class AB implements A, B {
    @Override public String who() { return A.super.who() + B.super.who(); }
}
```

Когда что брать: интерфейс для контракта и «умения» (`Printable`, `Comparable`); абстрактный класс, когда есть общее
состояние и общая реализация. Если оба варианта подходят, предпочитайте интерфейс: класс может реализовать много, но
наследовать только один.

### Приведение типов и `instanceof`

Если у `Shape` нет метода, а есть только у интерфейса `Printable`, получить его из `Shape` можно приведением:

```java
((Printable) shape).print();          // ClassCastException, если shape не реализует Printable
if (shape instanceof Printable p) {   // безопасно: проверка и приведение в одном выражении
    p.print();
}
```

Приведение «вниз» компилируется всегда, а ошибку (`ClassCastException`) даёт только в рантайме. Поэтому общий контракт
(`area()`) надо объявлять в базовом типе `Shape`, и тогда приведения не нужны: `shape.area()` работает для любой фигуры.
Аналог в C#: `as` / `is` с шаблоном.

### Параметры конструктора: примитив или обёртка

Если значение всегда есть, берите примитив: `Circle(double radius)`. Параметр `Integer radius` допускает `null`, и
`this.radius = radius` (поле `double`) молча распаковывает его: `new Circle(null, "x")` компилируется и падает с
`NullPointerException` внутри конструктора. С параметром `double` такой вызов не скомпилируется. `double` принимает и
целые (`new Circle(25, ...)`), и дробные значения.

## Порядок инициализации

Для `new Child()` (проверено запуском) порядок такой:

1. статические блоки и статические поля **родителя**, затем **наследника** (один раз, при первой загрузке класса);
2. поля и блоки инициализации экземпляра **родителя** (в порядке записи);
3. **конструктор родителя**;
4. поля и блоки инициализации экземпляра **наследника**;
5. **конструктор наследника** (после вызова `super(...)`).

Помощник `log(...)` из `task5` нужен, чтобы инициализатор **поля** тоже что-то печатал: поле вида
`private String f = log("Parent: поле");` вычисляет значение при создании объекта.

Ожидаемый вывод для двух вызовов `new InitChild()`, где `InitChild extends InitParent` (проверено запуском):

```
Parent: статический блок      ← первый new: статика родителя, затем наследника (один раз)
Child: статический блок
Parent: поле                  ← поля и блоки родителя в порядке записи
Parent: блок экземпляра
Parent: конструктор           ← конструктор родителя целиком, ДО полей наследника
Child: поле
Child: блок экземпляра
Child: конструктор
----
Parent: поле                  ← второй new: статические блоки не повторяются
Parent: блок экземпляра
Parent: конструктор
Child: поле
Child: блок экземпляра
Child: конструктор
```

Две детали, на которых легко ошибиться:

- **без `extends` порядок родитель → наследник не проявится**: у двух независимых классов нет цепочки вызова `super()`;
  наследование в `class InitChild extends InitParent` обязательно;
- статический блок срабатывает при первом обращении к классу (первый `new`), а не при каждом: поэтому второй `new`
  начинается сразу с полей.

Из этого вытекает классический баг.

### Баг: вызов переопределяемого метода из конструктора

```java
class Base {
    Base() { hello(); }                  // шаг 3: вызываем метод, который переопределён
    void hello() { }
}
class Child extends Base {
    private String name = "Alex";        // присваивается на шаге 4, то есть ПОЗЖЕ
    @Override void hello() { System.out.println(name); }   // напечатает null
}
new Child();   // null
```

К моменту вызова `hello()` конструктор родителя ещё не закончил, а поля наследника **ещё не инициализированы**
(у них значения по умолчанию: `null`, `0`, `false`), даже если у них есть инициализатор. Объект используется в
«наполовину построенном» состоянии.

Отличие от C#: там инициализаторы полей наследника выполняются **до** конструктора базового класса, поэтому
переопределённый метод видит значение из инициализатора (но не значение, присвоенное в теле конструктора). Java
ведёт себя иначе: инициализаторы наследника идут после `super(...)`.

Как избегать: не вызывайте из конструктора методы, которые можно переопределить (делайте их `final` или `private`),
либо выносите инициализацию в фабричный метод.

### Код до `super(...)` (Java 25)

Раньше `super(...)` обязан был быть первой инструкцией конструктора. В Java 25 (JEP 513, «flexible constructor bodies»)
перед `super(...)` можно выполнять код, если он не обращается к `this`: например, проверить и подготовить аргументы:

```java
Chi(int raw) {
    if (raw < 0) throw new IllegalArgumentException("neg");   // допустимо в Java 25
    int fixed = Math.abs(raw);
    super(fixed);
}
```

`this(...)` вызывает другой конструктор того же класса (цепочка конструкторов, аналог `: this(...)` в C#).

## Тесты на `double`

В [ShapeTests.java](../../../../../../test/java/com/sandbox/core/oop/ShapeTests.java) площади сравниваются так:

```java
assertEquals(2, rectangle.area());                          // допустимо: у JUnit 5 есть версия без допуска
assertEquals(28.274333882308138, circle.area(), 1e-9);      // лучше: с допуском (delta)
```

`assertEquals(double, double)` без допуска **компилируется и работает** (поэтому IDE ничего не подчёркивает), но хрупко:
точное сравнение проходит только если ожидаемое и фактическое посчитаны буквально одинаковыми операциями.
Проверено запуском:

- `0.1 + 0.2 == 0.3` даёт `false` (результат `0.30000000000000004`);
- `Math.PI * r * r` и `Math.PI * Math.pow(r, 2)` отличаются в последних битах у 262 из 1000 радиусов (первый `r = 11`).

Правила: ожидаемое значение берите из независимого источника, а не копируйте формулу из кода (тест, повторяющий
реализацию, ничего не проверяет), и задавайте допуск `delta` (`1e-9` для обычных вычислений). Точное сравнение допустимо
только для значений, которые представимы точно (целые, `0.5`, `0.25`). Для `NaN` версия без допуска считает его равным
`NaN`, а `0.0` и `-0.0` различает.
